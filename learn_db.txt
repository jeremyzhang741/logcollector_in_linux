  一、先修知识地图

  在读代码前，需要建立这些基础概念。标 ⭐ 的是必须先懂的。

  ⭐ 存储基础

  ┌─────────────────┬───────────────────────────────────────────────────────────────┐
  │      概念       │                             要点                              │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ Page / Block    │ 磁盘 I/O 的最小单位（通常 8KB），数据库所有读写以 page 为粒度 │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ Buffer Pool     │ 磁盘 page 在内存中的缓存，类比操作系统的 page cache           │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ WAL（预写日志） │ 修改落盘前必须先写日志，保证崩溃可恢复                        │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ Checkpointing   │ 定期把内存脏页刷盘，缩短崩溃恢复时间                          │
  └─────────────────┴───────────────────────────────────────────────────────────────┘

  ⭐ 事务基础

  ┌────────────────┬────────────────────────────────────────────────────┐
  │      概念      │                        要点                        │
  ├────────────────┼────────────────────────────────────────────────────┤
  │ ACID           │ 原子性、一致性、隔离性、持久性                     │
  ├────────────────┼────────────────────────────────────────────────────┤
  │ MVCC           │ 多版本并发控制：读不阻写、写不阻读，通过版本链实现 │
  ├────────────────┼────────────────────────────────────────────────────┤

  ├────────────────┼────────────────────────────────────────────────────┤
  │ Redo Log / WAL │ 记录操作后的状态，用于崩溃恢复                     │
  └────────────────┴────────────────────────────────────────────────────┘

  ⭐ 并发控制基础

  ┌──────────┬────────────────────────────────────────────────────────────┐
  │   概念   │                            要点                            │
  ├──────────┼────────────────────────────────────────────────────────────┤
  │ Latch    │ 短期内存锁（读写锁），保护数据结构访问，dstore 里叫 LWLock │
  ├──────────┼────────────────────────────────────────────────────────────┤

  ├──────────┼────────────────────────────────────────────────────────────┤
  │ 两者区别 │ Latch 是实现机制，Lock 是数据库语义，不要混淆              │
  └──────────┴────────────────────────────────────────────────────────────┘

  三、核心数据结构（必须先掌握）

  1. Page 格式

  磁盘上的一个 page（8KB）：

  ┌────────────────────────────────┐ ← page 起始
  │  PageHeader                    │
  │  - checksum                    │
  │  - GLSN / PLSN（WAL 位置）     │
  │  - pageType                    │
  │  - flags                       │
  ├────────────────────────────────┤
  │  DataHeader（data page 特有）  │
  │  - tdCount（TD 槽数量）         │
  │  - freespace 指针              │
  ├────────────────────────────────┤
  │  TD 槽区（TD[0], TD[1], ...）  │
  │  每个 TD: XID, CSN,            │
  │           undoPtr, status      │
  ├────────────────────────────────┤
  │  ItemId 数组（offset 索引）    │  ← 从低地址向高地址增长
  ├────────────────────────────────┤
  │         （空闲区域）           │
  ├────────────────────────────────┤
  │  Tuple 数据（从高到低增长）    │  ← 从高地址向低地址增长
  └────────────────────────────────┘

  关键文件：
  - include/page/dstore_page.h — PageHeader
  - include/page/dstore_data_page.h — DataPage（含 TD 区）
  - include/page/dstore_heap_page.h — HeapPage

  2. Tuple 格式

  // include/tuple/dstore_heap_tuple.h
  struct HeapDiskTuple {
      uint8     m_tdId;        // 指向页内 TD 槽编号
      uint8     m_lockerTdId;  // 行锁持有者 TD
      uint16    m_size;        // tuple 总大小
      Xid       m_xid;         // 最后修改者 XID（缓存）

      uint32 m_tdStatus  : 2;  // DETACH / NEW_OWNER / HISTORY_OWNER
      uint32 m_liveMode  : 3;  // INSERT / UPDATE / DELETE 版本类型
      uint32 m_hasNull   : 1;
      uint32 m_numColumn : 11;
      // ...

      char m_data[];           // null bitmap + 列数据
  };

  3. TD（Transaction Descriptor）

  // include/page/dstore_td.h
  struct TD {
      uint64      m_xid;        // 当前占用者 XID
      CommitSeqNo m_csn;        // 提交 CSN（提交后填入）
      uint64      m_undoRecPtr; // 指向最新 undo 记录
      uint64      m_lockerXid;  // 行锁持有者
      CommandId   m_commandId;  // SQL 语句编号
      uint16      m_status : 2; // UNOCCUPY / IN_PROGRESS / END
      uint16      m_csnStatus:2;// IS_INVALID / IS_PREV / IS_CUR
  };

  4. XID 结构

  // include/transaction/dstore_transaction_types.h
  union Xid {
      uint64 m_placeHolder;
      struct {
          uint64 m_zoneId     : 20;  // Undo Zone 编号
          uint64 m_logicSlotId: 44;  // Zone 内事务槽编号
      };
  };

  5. Undo Record

  // include/undo/dstore_undo_record.h
  struct UndoRecordHeader {
      UndoType   m_undoType;      // INSERT / UPDATE / DELETE
      CommandId  m_cid;
      UndoTdInfo m_tdPreInfo;     // 操作前的 TD 快照（含旧 XID/CSN/undoPtr）
      uint64     m_txnPreUndoPtr; // 同事务上一条 undo 记录（链表）
      uint64     m_ctid;          // 被修改的 tuple 位置
      uint64     m_fileVersion;
  };

⏺ 多事务并发写同一页面的核心问题是：页面上的 TD 槽是有限的，多个事务竞争同一页面时如何安全地分配和回收 TD 槽。下面逐层拆解。

  ---
  一、并发的基础保障：页级排他锁

  所有写操作进入页面前必须持有 LW_EXCLUSIVE，这把锁保证了同一时刻只有一个事务在操作页面内容。

  T1 持有 PageA 的 LW_EXCLUSIVE → 执行 AllocTd + 写 Tuple
  T2 想写 PageA → 阻塞等待
  T3 想写 PageB → 不受影响，完全并行

  T1 释放锁 → T2 获得锁 → 继续

  所以"并发写同一页面"实际上是串行执行的，TD 分配逻辑在锁保护下不存在竞态。复杂性在于：T1 和 T2 先后写同一页面时，页面上会同时存在多个事务的 TD
   槽，如何管理这些槽位才是关键。

  ---
  二、TD 槽的容量

  // include/page/dstore_td.h
  constexpr uint8 DEFAULT_TD_COUNT = 4;    // 初始槽数
  constexpr uint8 EXTEND_TD_NUM    = 2;    // 每次扩展增加 2 个
  constexpr uint8 MAX_TD_COUNT     = 128;  // 上限

  一个新页面初始只有 4 个 TD 槽，可以动态扩展到 128 个。每个事务在某个页面上最多占用一个 TD 槽。

  ---
  三、AllocTd 完整决策树

  入口是 AllocTd()，它是一个带重试的外壳，内部调用 DoAllocTd()：

  // src/page/dstore_data_page.cpp:244
  TdId DataPage::AllocTd(TDAllocContext &context) {
      for (int i = 0; i < 100; ++i) {          // 最多重试 100 次
          tdId = DoAllocTd<pageType>(context);
          if (tdId != INVALID_TD_SLOT) break;
          GaussUsleep(10L);                     // 等 10 微秒再试
      }
  }

  DoAllocTd() 的四步决策（src/page/dstore_data_page.cpp:199）：

  DoAllocTd():

  Step 1: 扫描所有现有 TD 槽
    ├─ 发现 curXid 已有槽 → 直接复用（同一事务多次写同页面）
    ├─ 发现 UNOCCUPY_AND_PRUNEABLE 槽 → 记为 firstUseableTdSlot
    └─ 扫描结束

    if firstUseableTdSlot 有效 → 返回（直接用冻结槽）

  Step 2: 尝试回收已结束事务的 TD 槽（TryReuseTdSlots）
    → 找到可回收的 → 返回

  Step 3: （跳过，注释残留）

  Step 4: 扩展 TD 区域（ExtendTd）
    → 页面有足够空间 → 新增 2 个槽 → 返回
    → 空间不足 → 返回 INVALID_TD_SLOT

  失败 → 上层重试 100 次，每次间隔 10μs

  ---
  四、TryReuseTdSlots 核心逻辑

  这是最复杂的部分，处理"所有 TD 槽都被已结束事务占用"的场景。

  4.1 TDAllocContext：分配时的上下文

  // include/page/dstore_td.h:68
  struct TDAllocContext {
      CommitSeqNo recycleMinCsn;   // 当前所有活跃快照中最小的 CSN
                                    // 早于此 CSN 提交的事务对所有快照可见，可安全冻结
      Transaction *txn;
      TDAllocWALInfo allocTd;      // 记录本次分配操作的 WAL 信息
      TDReuseWaitInfo waitXids;    // 记录因进行中的事务无法回收时，需等待的 XID 列表
  };

  recycleMinCsn 是判断 TD 能否彻底释放的关键阈值。

  4.2 TryReuseOneTdSlot：对单个 TD 的判断

  对每个 TD 槽，查询其 XID 的当前状态，得出 TdReuseState：

  TdReuseState:

    TD_RECYCLE_UNUSED  ← 可以彻底清空
      条件：事务已 Frozen 或 (事务已 Committed 且 csn < recycleMinCsn)
      含义：所有活跃快照都能看到这个版本，不再需要通过 TD 查询历史

    TD_RECYCLE_REUSE   ← 可以复用但保留旧 CSN
      条件：事务已 Committed 且 csn >= recycleMinCsn
      含义：还有老快照可能需要这个 CSN 判断可见性

    TD_IS_IN_PROGRESS  ← 不可回收
      条件：事务还在进行中
      副作用：记入 waitXids，标记 canResetTd = false

    TD_CONTENT_UPDATED ← 不可回收（仅 Index 页）
      条件：事务已 Aborted
      副作用：需要先执行 Undo 回滚

    TD_IGNORE          ← 忽略（远端节点的 XID，tryLocalXidOnly 模式下跳过）

  4.3 TryReuseTdSlots 完整流程

  // src/page/dstore_data_page.cpp:344
  TryReuseTdSlots():

    bool canResetTd = true;
    // 存在进行中的事务时 canResetTd = false
    // 原因：进行中的事务如果之后 Abort，需要能把 tuple 回滚到 DETACH_TD
    //       但如果我们已经把某个 TD Reset 了，回滚时就找不到对应信息了

    for 每个 TD 槽:
      查询 XidStatus
      根据状态分类放入 tdRecycle[] 数组

    if tdRecycleNum > 0:
      RefreshTupleTdStatus()  // 批量更新页上所有相关 tuple 的 tdStatus
      GetAvailableTd()        // 选出一个槽返回
    else:
      return INVALID_TD_SLOT  // 所有槽都是进行中，分配失败

  4.4 RefreshTupleTdStatus：更新 tuple 状态

  遍历页上所有 tuple，找到指向被回收 TD 的 tuple，更新其 m_tdStatus：

  slot.unused == true（彻底冻结）：
    tuple.tdStatus → DETACH_TD
    含义：永久可见，不再需要查 TD

  slot.unused == false（保留历史）：
    tuple.tdStatus → ATTACH_TD_AS_HISTORY_OWNER
    含义：TD 被新事务占用，但旧 CSN 保留在 TD 里，读时用旧 CSN 判断可见性

  4.5 GetAvailableTd：选择最优槽位

  // src/page/dstore_data_page.cpp:506
  优先级：
    1. canResetTd && slot.unused → td->Reset() 彻底清空，返回（最干净）
    2. slot.unused 但 canResetTd=false → 有进行中的事务，不能 Reset
       （因为进行中的事务 Abort 时需要知道旧状态）
    3. slot 非 unused → td->SetStatus(OCCUPY_TRX_END)，保留旧 CSN
       从中选 CSN 最小的（最老的事务），它最快能变成 UNUSED

  五、ExtendTd：扩展 TD 区域

  当所有现有 TD 都被进行中的事务占用（无法回收）时，尝试在页面上物理扩展 TD 区域：

  // src/page/dstore_data_page.cpp:98
  ExtendTd():
    检查：tdNum < MAX_TD_COUNT（还能扩）
    检查：页面剩余空间 >= sizeof(TD)（有地方放）

    // 物理操作：ItemId 数组整体向后移动，给新 TD 腾位置
    memmove_s(start + numExtended * sizeof(TD), size, start, size)

    // 初始化新 TD 槽
    for i in [tdNum, tdNum + numExtended):
        GetTd(i)->Reset()

    dataHeader.tdCount += numExtended
    m_header.m_lower   += numExtended * sizeof(TD)

  注意：ExtendTd 会压缩页面可用空间，因为 TD 区域扩展占用了原来用于存 tuple 的空间。

  七、canResetTd 为什么重要

  当页面上存在进行中的事务时，canResetTd = false，不能对 TD 执行 Reset()：

  场景：
    TD[0] = T1（已提交），TD[1] = T2（进行中）
    T3 要复用 TD[0]

    如果 T2 之后 Abort：
      系统需要把 T2 修改的 tuple 回滚到之前的状态
      回滚时通过 tuple → tdId → TD 找到 undo 链
      如果 TD[0] 被 Reset 了，T2 Abort 时可能影响 TD[0] 的状态
      → 不安全

    所以 canResetTd=false 时：
      TD[0] 不执行 Reset()，而是 SetStatus(OCCUPY_TRX_END)
      保留旧 CSN（IS_PREV_XID_CSN），新事务 T3 写入时
      旧 CSN 通过 SetTd() 变为 IS_PREV_XID_CSN 保留

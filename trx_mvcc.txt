  ---
  核心设计思路

  dstore 的 MVCC 采用 Undo-based 旧版本重建 模式（不同于 PostgreSQL 的 append 多版本）：
  - 数据页上只存最新版本
  - 旧版本通过逆序回放 Undo 记录动态重建
  - 以 CSN（Commit Sequence Number） 作为可见性判断依据

  ---
  1. Tuple 头部结构

  include/tuple/dstore_heap_tuple.h：

  struct HeapDiskTuple : public DataTuple {
      union {
          struct TupleField {
              uint8     m_tdId;        // 指向页内 TD 槽位（最多256个）
              uint8     m_lockerTdId;  // 行锁持有者 TD
              uint16    m_size;
              Xid       m_xid;         // 最后修改该 tuple 的 XID（缓存用）
          };
      } m_ext_info;

      union {
          uint32 m_info;
          struct {
              uint32 m_hasNull     : 1;

          };

  };

  两个关键字段：

  3. 可见性判断主流程

  HeapPage::GetVisibleTuple() (src/page/dstore_heap_page.cpp:160)：

  读取页上 Tuple
       ↓
  获取 Tuple 的 TD（通过 m_tdId）
       ↓
  判断 m_tdStatus：

    DETACH_TD
      → needUndo = false（已冻结，直接可见）

    ATTACH_TD_AS_HISTORY_OWNER
      → needUndo = td->TestCsnStatus(IS_INVALID)
                 || !XidVisibleToSnapshot(snapshot, td->GetCsn())
      （CSN 无效或 TD 中记录的 CSN 不可见 → 需要查 Undo）

    ATTACH_TD_AS_NEW_OWNER
      → 判断是否是当前事务：
          是当前事务 → CidVisibleToSnapshot(td->GetCommandId())
          非当前事务 → XidVisibleToSnapshot(snapshot, xid)
       needUndo = !上述结果

       ↓
  needUndo == true → ConstructCrTuple()（逆序回放 Undo 重建旧版本）
  needUndo == false → 返回页上当前版本

  4. CSN 可见性判断

  include/transaction/dstore_transaction.h:628：

  // 已提交事务的 CSN 可见性（最常用路径）
  inline bool XidVisibleToSnapshot(Snapshot snapshot, CommitSeqNo csn) {
      return csn < snapshot->GetCsn();   // tuple 的提交时间 < 快照时间
  }

  // 命令级可见性（同一事务内）
  inline bool CidVisibleToSnapshot(Transaction *txn, Snapshot snapshot, CommandId cid) {
      return (!txn->IsCurCidUsed() && txn->GetCurCid() == snapshot->GetCid())
             || cid < snapshot->GetCid();
  }

  XidVisibleToSnapshot()完整版本处理的边界情况（dstore_transaction.cpp:1313）：

  XID → 查 XidStatus（先查 TD，再查 Undo Zone）
    ├── Frozen        → true（老事务，已冻结）
    ├── Aborted       → false
    ├── SNAPSHOT_DIRTY → true（脏读模式，见所有非 Abort）
    ├── PendingCommit → WaitForTransactionEnd() → 等待完成后重判 CSN
    ├── Committed     → csn < snapshot->GetCsn()
    └── InProgress    → false

  PendingCommit 是关键边界：Commit WAL 已写但 CSN 尚未最终落盘，需等待完成再比较。

  5. Undo 链回放重建旧版本

  HeapPage::ConstructCrTuple() (src/page/dstore_heap_page.cpp:875)：

  起点：页上最新 Tuple + 其 TD

  循环：
    1. 从 TD 获取 XID、CSN、UndoRecPtr
    2. FetchUndoRecordByMatchedCtid() 取该事务对此 Tuple 的 Undo 记录
    3. 判断该事务对快照是否可见：
         当前事务 → CidVisibleToSnapshot(record.GetCid())
         其他事务 → XidVisibleToSnapshot(snapshot, xid)
    4. 可见 → 检查 liveMode：
         DELETE / OLD_BY_ANOTHER_PAGE_UPDATE → 返回 nullptr（快照中此时已删）
         否则 → 返回当前 tuple 内容（重建完毕）
    5. 不可见 → ConstructCrTupleFromUndo(record) 从 Undo 恢复更老的版本
                 更新 tupleTdId → 继续循环

  ConstructCrTupleFromUndo() 按 Undo 类型还原：

  switch (record->GetUndoType()) {
      case UNDO_HEAP_DELETE:                              // 还原删前内容
      case UNDO_HEAP_INPLACE_UPDATE:                     // 还原原地更新前内容
      case UNDO_HEAP_SAME_PAGE_APPEND_UPDATE:            // 还原同页更新前内容
      case UNDO_HEAP_ANOTHER_PAGE_APPEND_UPDATE_OLD_PAGE: // 还原跨页更新前内容
  }

  6. TD 槽位复用机制（MVCC 关键设计）

  页内 TD 槽位有限（最多256个），已提交事务的 TD 必须回收复用。

  DataPage::TryReuseTdSlots() (src/page/dstore_data_page.cpp:344)：

  判断能否复用一个 TD：

  对每个 TD 槽：
    获取 XidStatus → 检查 CSN：

    TD_RECYCLE_UNUSED（完全冻结）：
      csn < recycleMinCsn（所有活跃快照的最小 CSN）
      → 不再有任何快照需要看此 TD 的旧版本
      → tuple 的 tdStatus 改为 DETACH_TD（永久可见）

    TD_RECYCLE_REUSE（保留 CSN）：
      事务已提交，但 csn >= recycleMinCsn
      → 仍有老快照可能需要判断此版本
      → tuple 的 tdStatus 改为 ATTACH_TD_AS_HISTORY_OWNER（保留 CSN 供判断）
      → 新事务占用此 TD，写入新 XID

    TD_IS_IN_PROGRESS：
      → 不可复用（事务进行中）

    TD_CONTENT_UPDATED（事务已 Abort）：
      → 不可复用（Undo 回滚尚未完成）

  RefreshTupleTdStatus() 批量更新页内所有指向被复用 TD 的 Tuple：

  ATTACH_TD_AS_NEW_OWNER → ATTACH_TD_AS_HISTORY_OWNER  （TD 将被新事务复用）
  ATTACH_TD_AS_NEW_OWNER → DETACH_TD                   （TD 完全冻结）

  这是 MVCC 正确性的关键：TD 复用后，老 Tuple 通过 ATTACH_TD_AS_HISTORY_OWNER 状态告知读者："请用 TD 中保留的旧 CSN 来判断可见性，需要时从 Undo
   重建"。

  7. 快照建立时机

  Transaction::SetSnapshotCsn() (dstore_transaction.cpp:1513)：

  SetThrdLocalCsn(MAX_COMMITSEQNO)    // 相当于"加锁"，阻止自己的 CSN 被纳入全局最小 CSN
  → GetNextCsn(csn, false)            // 读当前全局 CSN（不递增）
  → GetCursorSnapshotMinCsn()         // 考虑游标打开时的最小 CSN
  → SetThrdLocalCsn(min(csn, cursor)) // 释放锁，注册自己的快照 CSN
  → m_snapshot.SetCsn(csn)           // 设置快照

  - READ COMMITTED：每条 SQL 语句开始时重建快照 → 能看到语句开始前已提交的数据
  - TRANSACTION SNAPSHOT：事务开始时建立，整个事务共享同一快照

  ---
  整体流程图

  写事务（UPDATE）：
    ┌─────────────────────────────────────────────────────┐
    │ 1. AllocTd() 在页面分配 TD 槽（可能复用旧槽位）        │
    │ 2. 写 Undo Record（记录操作前的 TD 快照 + 旧 Tuple 数据）│
    │ 3. 更新页上 Tuple（写新版本内容 + 更新 TD: XID/UndoPtr）│
    │ 4. tuple.m_tdStatus = ATTACH_TD_AS_NEW_OWNER         │
    │ 5. 写 WAL（数据页 WAL）                               │
    │ 6. 提交 → CsnMgr 原子分配 CSN → TD.csn = newCsn      │
    └─────────────────────────────────────────────────────┘

  读事务（SELECT with snapshot CSN=S）：
    ┌─────────────────────────────────────────────────────┐
    │ 1. 扫描页面拿到最新 Tuple                             │
    │ 2. 查 Tuple.m_tdId → 对应 TD                         │
    │ 3. 判断 m_tdStatus：                                  │
    │      DETACH_TD           → 可见                       │
    │      ATTACH_TD_AS_HISTORY → td.csn < S ? 可见:查Undo  │
    │      ATTACH_TD_AS_NEW    → XidVisible(xid, S) ?      │
    │ 4. 不可见 → 逆序遍历 Undo 链重建历史版本              │
    │ 5. 找到第一个满足 csn < S 的版本返回                  │
    └─────────────────────────────────────────────────────┘

  ---
  核心优势：
  - 无版本链存储开销：历史版本不占用数据页空间，按需从 Undo 重建
  - TD 槽复用高效：recycleMinCsn 驱动 TD 快速冻结回收，减少 Undo 读取
  - CSN 单调比较：可见性判断退化为一次整数比较，无全局事务表扫描

  也就是说，tuple 落盘时 tdStatus 永远是 ATTACH_TD_AS_NEW_OWNER。

  ---
  另外两种状态是何时设置的？

  ATTACH_TD_AS_HISTORY_OWNER 和 DETACH_TD 不在写入时设置，而是在 TD 槽位被复用时由 RefreshTupleTdStatus() 批量更新：

  TD 复用（TryReuseTdSlots）
    ├── 事务已提交，但 csn >= recycleMinCsn（仍有老快照需要它）
    │     → ATTACH_TD_AS_NEW_OWNER → ATTACH_TD_AS_HISTORY_OWNER
    │     （告诉读者：TD 已被新事务占用，你需要去 Undo 找旧 CSN 判断可见性）
    │
    └── 事务已提交，且 csn < recycleMinCsn（所有活跃快照都不再需要它）
          → ATTACH_TD_AS_NEW_OWNER → DETACH_TD
          （告诉读者：这条 tuple 对所有快照永远可见，不用查 TD）

  ---
  状态转移总结

  写入
    └─ ATTACH_TD_AS_NEW_OWNER   ← 所有 DML 落盘时的初始状态
            │
            │ TD 复用（RefreshTupleTdStatus）
            ├─→ ATTACH_TD_AS_HISTORY_OWNER   （TD 被新事务占用，但旧快照还需要旧 CSN）
            │
            └─→ DETACH_TD                   （事务足够老，永久可见，TD 完全释放）

  所以三种状态代表了 tuple 的"与 TD 关系"的不同阶段，ATTACH_TD_AS_NEW_OWNER 是起点，另外两种状态是 TD 回收时的惰性更新结果。

⏺ 这是理解 dstore MVCC 的关键点。答案很直接：TD 槽位是页内的有限资源，当新事务写入需要 TD 槽而页面已满时，必须回收旧事务的 TD
  槽，回收前必须更新所有指向该槽的 tuple。

  ---
  为什么必须更新 tdStatus？

  问题根源：每页的 TD 槽数量有限（最多256个）。

  场景：

  页面有 N 个 TD 槽，全部被已提交事务占用
            ↓
  新事务要写入这个页面，需要一个 TD 槽
            ↓
  必须回收一个旧事务的 TD 槽给新事务用
            ↓
  回收后，新事务会覆盖这个 TD 的 XID/CSN 内容
            ↓
  原来指向这个 TD 的 tuple 怎么办？

  如果不更新这些 tuple 的 tdStatus，读取时用 tuple.m_tdId 去查 TD，得到的是新事务的 XID/CSN，可见性判断就完全错了。

  ---
  回收前做什么

  TryReuseTdSlots() → RefreshTupleTdStatus() 遍历页上所有 tuple，把指向被回收 TD 的 tuple 更新：

  // src/page/dstore_data_page.cpp:496-500
  if (slot.unused) {
      // TD 完全释放（事务足够老，所有快照都可见）
      SetTupleTdStatus<tup_type>(offset, DETACH_TD);
  } else {
      // TD 被新事务复用，但旧 CSN 仍保留在 TD 中
      SetTupleTdStatus<tup_type>(offset, ATTACH_TD_AS_HISTORY_OWNER);
  }

  两种情况的含义：

  DETACH_TD：TD 彻底清空（td->Reset()），tuple 与 TD 断开关系。读取时直接判定该 tuple 对所有快照永远可见，不再需要查 TD。

  ATTACH_TD_AS_HISTORY_OWNER：TD 槽被新事务占用，但 TD 的旧 CSN 被刻意保留（TD 状态设为 OCCUPY_TRX_END，不 Reset）。tuple 保留对该 TD
  槽的引用，读取时用 TD 里保留的旧 CSN 来判断可见性，如果不可见再去 Undo 链找更老版本。

  ---
  代码中的保留逻辑

  GetAvailableTd() (src/page/dstore_data_page.cpp:528)：

  } else if (!td->TestStatus(TDStatus::UNOCCUPY_AND_PRUNEABLE)) {
      td->SetStatus(TDStatus::OCCUPY_TRX_END);  // 保留 CSN，不 Reset
      // 选 CSN 最小的那个槽给新事务用
      if (td->TestCsnStatus(IS_CUR_XID_CSN) && td->GetCsn() <= csn) {
          firstCommitTdSlot = slot.id;
          csn = td->GetCsn();
      }
  }

  为什么选 CSN 最小的？因为 CSN 越小说明事务越老，越早会低于所有活跃快照的 recycleMinCsn，届时 tuple 就能升级为 DETACH_TD，彻底脱离 TD。

  ---
  完整流程

  新事务需要 TD 槽，页面已满
           ↓
  TryReuseTdSlots()
    ├─ 找出所有已结束事务的 TD
    ├─ csn < recycleMinCsn（所有活跃快照都不再需要）
    │     → slot.unused = true
    └─ csn >= recycleMinCsn（还有老快照可能用到）
          → slot.unused = false
           ↓
  RefreshTupleTdStatus()  ← 遍历页上所有 tuple，in-place 修改
    ├─ slot.unused == true  → tuple.tdStatus = DETACH_TD
    └─ slot.unused == false → tuple.tdStatus = ATTACH_TD_AS_HISTORY_OWNER
           ↓
  GetAvailableTd()
    ├─ unused 的 TD → td->Reset()，分配给新事务
    └─ 非 unused 的 TD → 保留旧 CSN（不 Reset），分配给新事务写入新 XID

  本质：这是一种惰性清理设计。tuple 提交时不立即更新 tdStatus，而是推迟到有新写入需要回收 TD 槽时才做批量更新。代价是每次回收 TD
  时需要扫描页上所有 tuple，收益是避免了提交路径上的额外页面写入。

⏺ 这是整个 MVCC 设计中最精妙的部分。现在有了完整的证据链，可以准确回答这个问题。

  关键：SetTd() 是入口

  当新事务 T2 占用被复用的 TD 槽时，调用 SetTd()（include/page/dstore_data_page.h:158）：

  inline void SetTd(uint8 tdId, Xid xid, UndoRecPtr undoPtr, CommandId commandId)
  {
      TD *td = GetTd(tdId);

      if (td->GetXid() != INVALID_XID && td->GetXid() != xid) {
          if (td->TestCsnStatus(IS_CUR_XID_CSN)) {
              td->SetCsnStatus(IS_PREV_XID_CSN);  // ← T1的CSN降级为"历史CSN"
          } else if (td->TestCsnStatus(IS_PREV_XID_CSN)) {
              // 已经是历史CSN了，保持不变
          }
      }

      td->SetXid(xid);            // 覆写为 T2 的 XID
      td->SetUndoRecPtr(undoPtr); // 覆写为 T2 的 undo 指针
      td->SetStatus(OCCUPY_TRX_IN_PROGRESS);
  }

  TD 此时的状态：

  XID       = T2 (新事务)
  CSN       = 100 (T1的，保留)
  csnStatus = IS_PREV_XID_CSN  ← 这是关键标记
  undoPtr   = T2的第一条undo记录
  status    = IN_PROGRESS

  ---
  T2 提交时做什么

  T2 提交时，CSN 写入undo zone 的 transaction slot，不写回页面 TD。

  页面 TD 的 CSN 通过 FillCsn() 惰性更新：

  // src/page/dstore_page.cpp:136
  CommitSeqNo TD::FillCsn(Transaction *transaction, ...) {
      if (TestCsnStatus(IS_CUR_XID_CSN)) return m_csn;  // 已有则跳过

      // IS_PREV_XID_CSN 不命中上面的 early return，会继续执行：
      if (inXidStatus->IsCommitted()) {
          m_csn = inXidStatus->GetCsn();          // 覆写为 T2 的 CSN
          m_csnStatus = IS_CUR_XID_CSN;
      }
  }

  FillCsn() 在下次 TD 回收（TryReuseOneTdSlot）时才被调用，不在提交路径上。

  ---
  HISTORY_OWNER tuple 的可见性判断

  GetVisibleTuple() 对 ATTACH_TD_AS_HISTORY_OWNER：

  needUndo = td->TestCsnStatus(IS_INVALID) || !XidVisibleToSnapshot(snapshot, td->GetCsn())

  FillCsn 调用前（TD 还是 IS_PREV_XID_CSN，CSN=100）：
  - snapshot=150 → !XidVisible(150, 100) = false → 不需要 undo，直接返回 T1 的 tuple ✓

  FillCsn 调用后（TD 已是 IS_CUR_XID_CSN，CSN=T2_csn=200）：
  - snapshot=150 → !XidVisible(150, 200) = true → 进入 undo 重建

  ---
  Undo 链跨事务跳转（最关键的设计）

  进入 ConstructCrTuple 时，crTd 里 XID=T2，undoPtr=T2的 undo 链头。但这条 CTID 可能是 T1 改的，T2 根本没碰过它。

  FetchUndoRecordByMatchedCtid（src/transaction/dstore_transaction_mgr.cpp:825）：

  while (true) {
      FetchUndoRecord(undoRec, curPtr, curXid);

      if (undoRec->IsMatchedCtid(ctid)) break;  // 找到了，退出

      // 没找到：检查 undo 记录里记录的"上一个 TD 拥有者"
      if (undoRec->GetTdPreXid() != curXid && undoRec->GetTdPreXid() != INVALID_XID) {
          // TD 曾被前一个事务持有，跳转过去！
          *matchedCsn = undoRec->GetTdPreCsn();  // 更新为 T1 的 CSN
      }
      curXid = undoRec->GetTdPreXid();       // 跳转到 T1 的 XID
      curPtr = undoRec->GetTdPreUndoPtr();   // 跳转到 T1 的 undo 链
  }
  xid = curXid;  // 返回时把 xid 更新为匹配到的事务

  每条 undo 记录里存储了写入时的 TD 前状态（UndoTdInfo m_tdPreInfo），其中包含 T1 的 XID 和 undo 指针。 当遍历 T2 的 undo 链找不到这个 CTID
  时，通过 T2 第一条 undo 记录的 TdPreInfo 跳转到 T1 的 undo 链继续搜索。

❯ 这里提到t1和t2两个事务修改使用的td都是同一个tuple的td吗

⏺ 不是同一个 tuple。T1 和 T2 共享的是同一个 TD 槽位，但各自修改的可以是页面上完全不同的 tuple。

  ---
  TD 槽位是页级资源，不是 tuple 级

  一个页面有多个 TD 槽（最多256个），一个事务在同一页面上只需要一个 TD 槽，该事务在这个页面上修改的所有 tuple 都指向同一个 TD。

  页面结构：
  ┌─────────────────────────────────┐
  │  TD[0]: XID=T1, CSN=100        │  ← T1 占用的槽位
  │  TD[1]: XID=T3, ...            │
  │  TD[2]: UNOCCUPIED             │
  │  ...                           │
  ├─────────────────────────────────┤
  │  Tuple A: tdId=0, NEW_OWNER    │  ← T1 修改的
  │  Tuple B: tdId=0, NEW_OWNER    │  ← T1 修改的
  │  Tuple C: tdId=1, NEW_OWNER    │  ← T3 修改的
  │  Tuple D: (空闲)               │
  └─────────────────────────────────┘

  ---
  TD[0] 被 T2 复用的场景

  T2 进来需要一个 TD 槽，TD[0] 被选中复用（T1 已提交但 CSN 还不够老）：

  TD[0] 被 T2 复用后：
    XID=T2, CSN=100(T1保留), csnStatus=IS_PREV_XID_CSN, undoPtr=T2_undo

  Tuple A: tdId=0, ATTACH_TD_AS_HISTORY_OWNER  ← T1 修改的，TD被复用
  Tuple B: tdId=0, ATTACH_TD_AS_HISTORY_OWNER  ← T1 修改的，TD被复用
  Tuple D: tdId=0, ATTACH_TD_AS_NEW_OWNER      ← T2 新插入的（完全不同的 tuple）

  T2 修改的是 Tuple D（全新插入），完全没有碰 Tuple A 和 B。

  ---
  那 undo 跨链跳转是怎么建立的？

  T2 写 Tuple D 时，创建 T2 的第一条 undo 记录，此时 TD[0] 里还残留 T1 的信息：

  T2 第一条 undo 记录：
    ctid     = Tuple D 的 CTID
    TdPreInfo = { XID=T1, CSN=100, undoPtr=T1_last_undo }  ← 记录了 TD 复用前的状态

  这条 undo 记录建立了"T2链 → T1链"的跳转桥梁。之后再读 Tuple A（HISTORY_OWNER）时：

  FetchUndoRecordByMatchedCtid(xid=T2, ctid=TupleA_CTID):
    遍历 T2 的 undo 链：
      T2的undo记录(TupleD) → ctid不匹配
      读到 TdPreXid=T1 → 跳转到 T1 的 undo 链
      T1的undo记录(TupleA) → ctid匹配！找到了

  跳转桥梁只建立在 T2 的「第一条」undo 记录里（那时 TD 还残留 T1 的信息）。T2 后续的 undo 记录里 TdPreXid 就是 T2 自己了，不再有跨链信息。


❯ 最后也就是说td[0]这个槽位记录了所有t1和t2的undo记录吗

⏺ 不是。TD 槽位本身不存储 undo 记录，它只存储一个指针。

  ---
  TD 槽位里只有一个 undoPtr

  TD[0] 在 T2 写入后：
    XID     = T2
    undoPtr = T2的最新undo记录地址   ← 只有一个指针，指向 T2 的链尾
    CSN     = 100 (T1的，IS_PREV_XID_CSN)

  undo 记录本身存储在 undo zone（独立的存储区域），不在页面上。

  ---
  undo 链的真实结构

  T1 和 T2 各有自己独立的 undo 链，通过每条 undo 记录内部的 m_txnPreUndoPtr 串联：

  Undo Zone：

  T1 的链：
    [T1_undo_1: TupleA, TdPreInfo={INVALID}] ← T1的第一次写
          ↑ m_txnPreUndoPtr
    [T1_undo_2: TupleB, TdPreInfo={XID=T1,...}]  ← T1的第二次写（TD已是T1）
          ↑
    T1_last_undo（TD[0]被复用前 undoPtr 指向这里）

  T2 的链：
    [T2_undo_1: TupleD, TdPreInfo={XID=T1, undoPtr=T1_last_undo}]  ← 桥梁在这里
          ↑ m_txnPreUndoPtr
    [T2_undo_2: TupleE, TdPreInfo={XID=T2,...}]
          ↑
    TD[0].undoPtr 指向这里（T2的链尾）

  TD[0] 的 undoPtr 始终只指向当前事务（T2）的最新 undo 记录。跨到 T1 链的能力来自 T2_undo_1 内部存储的 TdPreInfo，而不是 TD 槽位本身。
